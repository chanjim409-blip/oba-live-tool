# 人工验证窗口交接

问题：独立回复浏览器为headless，检测到平台验证后保持阻断，但没有把窗口交给用户处理的入口；强制结束进程树的现场操作被自动审批拒绝，未执行。

新增受现有Bearer/Origin保护的接口：
- `POST /reply/manual-verification/open`，JSON `{"confirmed":true}`：先阻断动作，再关闭本程序拥有的浏览器上下文，使用原私有profile打开可见窗口。只导航，不操作验证码、不发送。
- `POST /reply/manual-verification/complete`，相同请求体：仅在用户明确完成后调用；关闭人工窗口，重新启动无头上下文，重新读取身份、房间、管理员与发送控件，检查通过才结束人工交接状态。业务场次不会自动恢复。
- `GET /reply/preflight` 增加 `manualState`，可见性如实报告；health在人工交接期间不声明回复执行可用。

任何已进入提交阶段的发送均拒绝通过人工登录入口重置，包括unknown/uncertain；必须另行核对。切换代次使旧身份与旧候选失效；人工窗口打开失败或重新核验失败继续拒绝发送。附着的外部浏览器不适用此交接，避免关闭非本程序拥有的上下文。

验证：22项宿主回归通过，包含交接期间发送/刷新拒绝、上下文关闭顺序、失败持续阻断、成功返回后台及未知发送不被重置；TypeScript检查通过。仅合成与本机测试页面，未完成真实账号人工交接或公屏发送。

部署状态：源码待载入新宿主；原固定运行版本4272fa2仍在，未因本次修改获得新接口。原进程没有温和关闭接口，先解决受控服务切换，不能对旧版本调用新接口后误报窗口已打开。不得以重启清除限制后直接发送，仍需用户人工完成和独立复核。
